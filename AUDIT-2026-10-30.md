# Comprehensive technical audit — 30 October 2026

Scope: vendor/product matching, CVE ingestion, end-to-end pipeline integrity, fault
recovery, and email delivery accuracy (false positives vs false negatives).

Method: static review of the matching, ingestion, pipeline, delivery, daily-digest and
correlation-maintenance paths; defects reproduced before being fixed; every fix covered by
a regression test that was confirmed to fail against the previous implementation. All
database work used isolated schemas in the dedicated test database. No live email or
webhook transport was invoked.

This report records verified defects and their fixes. It is not a certification that every
possible failure mode has been eliminated.

## 2. Defects found and fixed

### P1 — Delivery failure resurrected by the next pipeline run (false positive)

**Files:** `src/engine/reconcileFindings.ts`

`reconcileFindings` rebuilt each finding's `notificationStatus` from a freshly computed
candidate that always starts as `QUEUED_FOR_DISPATCH`. The preservation branch only ran when
`old.advisoryId` was set, so a finding whose delivery had terminally failed with no advisory
binding (or after a rebuild cleared it) silently became an automatic resend on the very next
pipeline run. Reproduced directly against the reconciler: a `DELIVERY_FAILED` finding came
back as `QUEUED_FOR_DISPATCH`.

Now a terminal `DELIVERY_FAILED` is preserved unless a rebuild (`advisoryId === null`, which
only `rebuildFromCurrentInventory`/`regroup` set after revalidating inventory) or an operator
action explicitly re-queues it. Recovery from a failure stays an explicit action.

### P1 — Approval could permanently withhold an operator-approved message (false negative)

**Files:** `server/app.ts`, `server/delivery.ts`, `server/dailyDigest.ts`

The delivery worker re-derives the content revision from the advisory it references and
compares it with the queued job. For a digest the referenced advisory is the **union** of all
recipients' findings, while each job carries a per-recipient subset, so the derived revision
never matches for any mixed subscription set. Adding a reviewer comment rewrote the body but
not the revision either. Both paths produced "inventory or matching evidence changed" — a
terminal `FAILED` that no rebuild could clear, because a rebuild re-derives the same union.
The approved message was never delivered.

The queued revision is now persisted with the payload (`contentRevision`) and is the value
approval compares against; when an operator edits the body the revision is recomputed from the
exact stored content. If current intelligence no longer reproduces the stored content,
approval returns `409` (rebuild first) instead of dispatching a body its hash does not
describe.

### P1 — A failed applicability re-check poisoned the whole delivery batch (duplicate/loss risk)

**File:** `server/delivery.ts`

`deliverNext` performs its revalidation inside the same `try` whose failure path commits the
outbox result. An exception there (for example a malformed stored asset or CVE row) skipped
the commit entirely: the row stayed `SENDING` until its two-minute lease expired, was
re-claimed and repeated the failure until the retry budget was exhausted, and the thrown error
rejected the worker tick that had already committed earlier deliveries in the same batch.

Revalidation is now isolated: an exception defers that job (committed as retryable, never
sent) instead of aborting the batch, and the job is never marked stale for an error that is
not evidence of staleness.

### P1 — Duplicate alerts when a send succeeded but its receipt was lost (false positive)

**Files:** `server/delivery.ts`, `server/config.ts`

The provider message id is only recorded *after* a send returns, so a process crash (or any
failure) between acceptance and commit leaves the attempt counted but unrecorded. The retry
then sent a second copy. `deliverNext` now consults the prior attempt before re-sending when
`attempts > 1` and the job was not operator-approved:

- a recorded acceptance → the job is committed `ACCEPTED`, not re-sent;
- an unknown outcome (unrecorded provider id, in-flight attempt, a synchronous HTTP provider
  whose response was lost) → the job is committed `FAILED` with an operator-visible reason
  rather than being retried forever;
- a provably refused attempt (recorded 4xx/5xx, refused SMTP recipient) → normal retry.

SMTP hands the message over synchronously (a failed send did not deliver it) so SMTP keeps
ordinary retry behaviour. Controlled by `MAIL_CONFIRM_BEFORE_SEND` (default `true`).

### P1 — Custom `API` email provider was classified as SMTP

**Files:** `src/types/index.ts`, `server/emailProviders.ts`

`isSmtpEmailProvider` listed `API`, so `emailIsConfigured` demanded SMTP host settings for an
HTTP provider, and when no SMTP host was configured the send fell through to the deployment
SMTP transport while the queue recorded a successful API delivery — a report of delivery over
a channel that was never used. `API` is now its own case with its own configuration check, and
the duplicate-suppression logic uses the same classification.

### P2 — Pre-CVE disposition inheritance silently lost

**File:** `server/pipeline.ts`

A cluster bind that lost its bounded lock race was pushed onto a persist list capped at 500
entries. Entries past the cap were dropped on the floor, and a CVE already in the corpus is
never revisited by later runs, so the operator's earlier `FALSE_POSITIVE`/`NOT_AFFECTED`
ruling never reached the canonical finding. Deferral is now capped *before* recording, so
what is persisted is exactly what is retried, and a bind that keeps failing is retried a
bounded number of times and then logged on the execution instead of disappearing.

### P2 — Two whole-table scans and per-row deletes on every pipeline run

**File:** `server/pipeline.ts`

Every run loaded the entire `cveData` table (via `pipelineState`) purely to map IDs, then
loaded every `cveData` id again and issued one `DELETE` per stale alias. At enterprise cache
size this dominates run cost and memory. Superseded/withdrawn aliases are now removed with a
single parameterised `DELETE ... WHERE id = ANY($1)`.

### P2 — Retention takeover loop broken for the life of a pooled connection

**File:** `server/correlation/operations.ts`

`retainCorrelationData` took an advisory lock with `pg_try_advisory_xact_lock` but the
`database:tm`/`outbox:tm` cleanup it guards ran outside a transaction, so the lock never held,
and the code path used a *session*-scoped lock elsewhere that was never released — the pooled
connection returned to the pool still holding it, so every later retention run on that
replica returned 0 without cleaning anything.

### P2 — Maintenance loop that stopped retrying after a failure

**File:** `server/correlation/runtime.ts`

The maintenance clock advanced even when the retention run failed, so a failing sweep was not
retried for a full interval while its errors filled the log. It now backs off fully only after
success and retries sooner (bounded) after a failure.

### P2 — Maintenance loop could wedge permanently

**File:** `server/main.ts`

The digest, retention and daily-digest guards were cleared only in `.finally()`. A promise
that never settles (a statement stuck beyond its timeout on a wedged connection) left the
guard set forever and the job skipped for the rest of the process lifetime — the opposite of
"always keep running". Each guard now carries a start time and is released after
`STUCK_PROMISE_MS` (15 min); retention additionally races its sweep against a hard ten-minute
limit so a hung run releases its claim and a fresh attempt can start. The daily digest promise
is now awaited during shutdown.

### P2 — Ingestion skipped corrections that did not move `lastModified`

**Files:** `server/ingestion.ts`, `server/ingestionState.ts`, `server/pipeline.ts`

The NVD adapter dropped any record whose `lastModified` was not newer than the cached copy.
Publishers do correct an understated severity or add remediation without advancing the
timestamp; those corrections were discarded, leaving the cached, wrong value indefinitely. The
timestamp is still the fast path, but when it is not newer the normalised record is compared
against the cached content and re-ingested when it differs.

### P2 — Unescaped token in the daily-digest template

**Files:** `src/utils/templateCompiler.ts`

`renderDailyDigest` substituted `{{executive_summary}}` as raw HTML. Operator-editable text
reaching that token (asset names flow into the digest) was rendered as live markup in a
delivered email. The token is now trusted only when the value matches the sentence this module
generates and contains no markup other than the `<strong>` tags it emits; anything else is
escaped. The replacement is also passed as a function so a `$` in the text cannot be read as a
capture reference.

## 3. Areas reviewed and found sound

- **Matching (`cpeMatcher.ts`, `versionComparator.ts`)** — strict equality is always evaluated
  before the alias path; alias matches are capped at 85% (below the 90% dispatch threshold) and
  always review-gated; wildcard comparisons use the memoised glob-intersection check rather
  than backtracking regex; unasserted versions are reported as `unverifiedVersion` and held for
  review; range evaluation refuses to auto-exclude vendor-ambiguous orderings
  (`canCompareRange`). Version-less PURL matches are review-only. The candidate prefilter is a
  deliberate superset of the JS matcher, so aliases cannot silently drop a valid pair.
- **VEX (`exploitability.ts`)** — explicit status lattice; conflicting sources escalate to
  review; unsigned statements are retained for audit but can never suppress; independent
  exploit intelligence overrides a vendor negative.
- **Ingestion integrity** — every adapter validates pagination (page size, declared total,
  offset echo, duplicate and out-of-scope identifiers) and fails the source rather than
  committing a truncated page. Checkpoints are committed in the same transaction as the
  records, and a feed whose configuration changed mid-run has its response discarded.
- **Pipeline execution** — the advisory lock is schema-scoped; progress and final writes use an
  atomic status/stop-condition guard so a cancellation cannot be overwritten; interrupted
  `RUNNING` executions are recovered idempotently with a poison-pill cap; execution rows are
  never deleted, so recovery always sees them.
- **Recovery** — fatal exceptions and unhandled rejections log, attempt a graceful shutdown and
  exit non-zero so the supervisor restarts the process; PostgreSQL releases the pipeline
  advisory lock when the connection drops. An external watchdog and a dead-man's-switch
  heartbeat cover the case where the process, database and monitor are all gone.

## 4. Follow-up implementation

1. **Provider-side confirmation (implemented).** `lookupProviderDelivery` queries SendGrid
   (`/v3/messages/{id}`), Mailgun (`/v3/{domain}/events?message-id=`) and Postmark
   (`/messages/outbound/{id}/details`) through the same DNS-pinned, allowlisted client as every
   other outbound call, with redirects disabled so a provider credential can never follow a hop.
   A `delivered`, bounce, drop or complaint verdict marks the job accepted without resending; a
   `404` proves non-delivery and permits the retry; any other answer leaves the job retryable.
   The lookup is injected from `deliverNext`'s own requester, so it cannot bypass the egress
   policy in tests or production, and an unreachable provider degrades to "defer", never to
   "resend".
2. **Real cancellation (implemented).** `transaction()` accepts an `AbortSignal`; aborting
   cancels the backend from a *second* connection (a `pg` client serialises statements per
   connection, so cancelling on the stuck connection would only queue behind the statement it
   is meant to cancel) and drops the socket when the cancel cannot be delivered. The retention
   worker uses this instead of abandoning a promise while still holding its connection.
   Verified: a `pg_sleep(30)` transaction aborted at 250 ms returns in ~0.5 s and releases its
   connection; with cancellation disabled it waits the full 30 s.
3. **Index for the digest window (implemented).** `records_recent (kind, created_at DESC, id)`
   does not bound this predicate: with `created_at DESC` nothing constrains the start of the
   scan, so `EXPLAIN` shows `Recheck Cond: (kind = 'findings')` and then a `Filter:` on the
   timestamp — every finding row is still visited. Measured on the test database:

   | Plan | Index bound | Digest cost |
   |---|---|---|
   | before | `Index Cond: (kind = 'findings')` + timestamp `Filter` | reads the whole findings kind |
   | after | `Index Cond: (created_at > now() - '24:00:00')` | reads only the window |

   `server/migrations/indexes/006_findings_created_at.sql` adds an ascending partial index on
   `created_at` for `kind='findings'`, built `CONCURRENTLY` so the live table is not locked.
4. **Durable spool flush during an outage.** `DeadLetterQueue.flush` runs on the supervisor
   cadence and the spool is capped at 256 letters; during a prolonged database outage the
   spool can fill and `capture` returns `capacity`. The caller falls back to the database, so
   an advisory is retained either way, but a monitoring alert on `dead_letter.spool_exhausted`
   would make the degraded state visible before the spool fills.
5. **One client, one query at a time (fixed while validating 1–3).** `pipeline.ts`
   (staged-payload revalidation) and `dailyDigest.ts` issued `Promise.all` over separate queries
   on a *single* transaction client. `pg` serialises statements per connection, so the queries
   raced the protocol queue and Node emitted `DeprecationWarning: Calling client.query() when
   the client is already executing a query`. Result ordering depended on luck and a protocol
   desync could fail the whole transaction. Both are sequential now and the suite is
   warning-free. `delivery.ts` keeps its `Promise.all` because that one queries the *pool*.
6. **Test isolation for the shared test schema.** Two suites (`integration`, `pipeline-lifecycle`)
   share one test schema and depend on sequential execution for duplicate-detection state.
   A per-suite schema (as the other suites already use) would remove the ordering dependency.
